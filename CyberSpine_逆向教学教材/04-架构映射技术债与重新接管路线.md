# 04：架构映射、技术债与重新接管路线

## 1. 用代码而不是名词理解架构

| 架构概念 | 当前对应代码 | 已经做到 | 尚未做到 |
|---|---|---|---|
| 感知末梢 | `WindowActivityPeripheral` + inventory/events/interactions | Windows 窗口元数据事实、事件合并、隐私最小化。 | 自动插件运行时、多末梢统一 lifecycle。 |
| 神经信封 | `NeuralMessage` | 基础字段、TTL、隐私级别、schema 名称。 | directive/proposal/result 的完整业务流。 |
| 中枢准入门 | `NeuralSignalGateway.publish` + `AdmissionPolicy` | session 路径的多层拒绝、限流、健康、审计、入队。 | legacy 路径等强度校验、控制面、路由。 |
| 持久脊髓 | `DurableEventQueue` | SQLite 状态、过期、折叠、ACK API。 | consumer、租约、重试、保留/清理政策。 |
| 当前上下文 | `CurrentContextStore` / `Reader` | 只读、deep copy、公共/元数据二次限制。 | 常驻 projector 与正式 MCP 接入。 |
| 上层适配器 | `adapters/mcp/context_server.py` | 单一只读 FastMCP tool 工厂。 | 入口、生命周期、认证/部署。 |
| 历史感知/大脑 | `SomaticPerceptorHub`、pacemaker、local model | 若干真实 I/O 与 demo 展示。 | 与上述新协议的桥接或迁移。 |
| 动作确认 | `SafetyGate`（旧） | 只读/需审批/关键字熔断的局部实现。 | 新架构下的“提议→具体用户确认→有限执行→持久审计”闭环。 |

## 2. 当前最大的事实断层

```text
                 已存在但没有调用边

WindowActivityPeripheral -> NeuralSpinalHub -> Gateway -> Queue -> ContextReader -> FastMCP
                         ^                                  ^                     ^
                         |                                  |                     |
                    tests construct                    no worker             no server main

                 另一个真实可启动、但历史的系统

cockpit / old MCP -> CyberSpineAppBridge -> SomaticPerceptorHub -> old perceptor signals
                                -> RealAutonomousPacemaker -> old buffer / old model / old actuator
```

这不是“最后补一个 import 就好”的断层。两边使用不同模型（`NeuralMessage` vs `RawSomaticSignal`）、不同生命周期、不同安全假设、不同输出目标。贸然把一个接到另一个会把历史 PoC 的隐私和动作路径带进新中枢，或把新中枢的安全约束绕开。

## 3. 已实现、mock、预留：重新接管时应如何判断

### 3.1 可以作为下一阶段基础的实现

- `WindowsWindowInventory` 的窗口枚举、WinEvent ticket 线程、200ms coalescing、可选输入活动聚合：Windows 平台的原生实现存在，且有细化的测试注入点。
- 统一 message 与 Pydantic 结构：可在纯 Python 单元测试中稳定构造。
- manifest/registration/session/admission、payload size/schema 限制：均有独立 core 测试文件。
- SQLite queue 的 message 保存、状态折叠和 TTL：实现是具体的，不依赖 README。
- context snapshot 的 immutable-by-copy 读法：代码短、边界清楚。

这些组件“已实现”不等于它们在一次用户启动中同时运行；它们是后续正式 runtime 可以复用的基础。

### 3.2 明确的测试/Mock 边界

- `tests/context` 通过注入 `catalog_provider`/snapshot 和临时数据库测试新 hub；没有 Windows 桌面或常驻服务。
- `tests/integration/test_window_gateway_contract.py` 用 fake catalog；它验证 message contract，而不是 Win32 + session runtime。
- gateway governance demo 用人工 clock、空 geometry `changes`、MemoryAuditSink。
- `plugins/examples/mock_storage_nerve` 是另一个 BNP 协议的示例，不会被新 gateway 自动读取。
- `demo_minimal_loop.py`、`IOPerceptorManager.mock_inject_storage_signal()`、通知/稳定性 perceptor 的 `mock_trigger_*` 都应被标作演示输入。
- 旧 app bridge 中插件商城、模型状态、供应商连接和部分简报是内存 dict / 文案；UI 呈现不证明安装或连接成功。

### 3.3 不能假称已完成的预留

1. 插件发现、签名/信任根、磁盘安装、runtime import/process 启动、JSONL transport、停止/重启与权限撤销。
2. 任何跨进程安全 session transport；当前 session 是内存对象。
3. 持久审计 sink、审计查询、审计保留/删除政策。
4. queue consumer、派送选择、ACK 身份验证、retry/backoff、dead-letter、终态清理。
5. health/isolation 的真实执行器；现在只会拒绝下一次 publish。
6. 新 hub 的 daemon、配置、优雅停机、日志、指标和资源生命周期。
7. context FastMCP 的启动/部署；`create_context_server` 没有 `run()` 调用点。
8. 新网关到用户确认、执行器和审计回写的动作链。
9. 多插件 schema registry 的可扩展机制；目前 validator 硬编码七个 window schema。

## 4. 最难理解、耦合最高、最可能技术债化的地方

### A. 双架构并存（最高优先级债务）

**证据：**启动的 cockpit/MCP 引用 `SomaticPerceptorHub` 和 `CyberSpineAppBridge`；新 `NeuralSpinalHub` 只被测试引用。

**难点：**文件名都用“神经/中枢/末梢”，但数据模型、入口和安全链不同。开发者很容易在旧 `app_bridge` 里加一个新 gateway 调用，以为完成迁移，实际形成双写或绕过。

**后果：**产品演示可见的东西与生产安全边界不一致；测试容易在旧路径绿、新路径不被执行。

**接管原则：**每个新需求先回答“属于新链的哪一个阶段”，不要在旧 `perceptors → pacing → app → mcp` 链上继续扩展。

### B. gateway 中的两条准入强度不同

**证据：**session 路径会走 `AdmissionPolicy`、limits、schema validators、flow/health；legacy `_admit_legacy()` 不走 limits/schema/flow/health。

**风险：**内置窗口末梢恰是当前 `NeuralSpinalHub` 的输入，最真实的装配却走较弱路径；monitor demo 走较强路径。这会制造“演示安全、装配不安全”的错觉。

**接管问题：**迁移 legacy 内置末梢到 manifest/session 前，要明确 runtime 如何安全地持有/传输 session；不能简单删 legacy 入口导致窗口链断开。

### C. `WindowActivityPeripheral` 是成熟但复杂的状态机

**证据：**同一类维护前台宽限、事实签名、目录 cache、几何 cache、焦点片段、未归因区间、交互 tracker、event coalescer、输入 hook 状态和七种消息生成。

**为什么复杂是合理的：**Windows 窗口事件是“变化提示”，不是完整事实；空前台、shell surface、拖动事件风暴和系统 UI 都需要防误报。

**为什么仍是债务风险：**大量私有可变字段耦合时序；修改一个消息或缓存规则易破坏另一个。最安全的维护方式是先读 `tests/sensing/test_window_activity.py` 中对应状态场景，再动极小变更，绝不将意图推断塞进该类。

### D. `CyberSpineAppBridge` 的服务定位器/展示态混合

**证据：**一个 constructor 同时创建 hub、buffer、actuator、model、telemetry、pacemaker，并保存插件商店、模型、Cortex 和简报字典。

**风险：**创建一个 MCP handler 就间接创建整套 app 服务；单例 pacemaker 和各 bridge/hub 的对象关系难以推断；硬编码状态会掩盖真正 runtime 未连接。

**定位：**这是旧 PoC 的主要耦合热点，不应该成为新主线的接入点。

### E. 旧动作安全链不等于当前安全不变量

`SafetyGate` 的确检查 risk、可选 approval callback 和一组危险关键词，但 `MasterCortex.process_intent_narrative()` 在没有 callback 时默认 `is_approved=True`，旧 MCP 可以构造 action 并调用 hub。它不具备新规则所需的带具体动作/目标/风险的持久确认与审计链。接管时应将它视作历史实现，不能用“有 SafetyGate”证明系统已安全完成。

## 5. 重新接管的阅读路线（面向暂时不能独立写代码的负责人）

每一步只需要回答一个问题；能答出再进入下一步。阅读时同时打开源文件与对应测试，先看函数名、输入、输出和调用者，不必先理解每一行 ctypes。

| 步骤 | 先看 | 你应该理解什么 | 自检问题 |
|---:|---|---|---|
| 0 | `pyproject.toml`、`scripts/*.bat` | 什么能启动，依赖是什么，为什么不存在一个唯一 CLI。 | “哪条命令会启动新 hub？”答案应是：当前没有。 |
| 1 | `src/core/neural_message.py` | 新世界里的一个消息有哪些字段、TTL 和 privacy 是什么。 | “state 与 event 为什么不同？” |
| 2 | `plugins/builtin/window_activity/manifest.json` | 一个具体内置末梢声明了哪些 topic/schema/privacy。 | “manifest 是否等于实际权限？”答案：否，还要 grant。 |
| 3 | `src/core/plugin_manifest.py`、`plugin_registration.py` | manifest→grant→session 的三层差别。 | “这段代码有没有启动 entrypoint？”答案：没有。 |
| 4 | `src/core/gateway_admission.py`、`gateway_errors.py` | 每一条上游消息为什么可能被拒绝。 | “payload 在哪一行以前不允许写入队列？” |
| 5 | `src/core/message_limits.py`、`schema_validation.py` | 结构和隐私不是文档约定，而是执行性白名单。 | “一个自称新 schema 的插件会怎样？” |
| 6 | `src/core/neural_gateway.py` | publish 的两条路径、审计前置、限流/健康所在位置。 | “legacy path 与 session path 少了什么？” |
| 7 | `src/core/event_queue.py` | SQLite 表、state collapse、event preservation、status 转换。 | “谁会消费 pending？”答案：当前没有人。 |
| 8 | `src/context/current_context.py`、`read_service.py`、`spinal_hub.py` | 入队成功后才投影、上下文为什么只读。 | “谁启动 NeuralSpinalHub？”答案：测试。 |
| 9 | `tests/core/`、`tests/context/`、`tests/integration/` | 哪些结论有 test contract，哪些 test 使用 fake。 | “哪一个测试真启动 Windows desktop？”通常没有。 |
| 10 | `src/sensing/window_events.py`、`window_inventory.py` | Windows callback 与真正事实读取为什么分线程/分职责。 | “callback 为什么不直接 publish？” |
| 11 | `src/sensing/window_activity.py`，配 `tests/sensing/test_window_activity.py` | 前台宽限、signature、七类消息、隐私字段。 | “一次窗口移动何时会产生 geometry event？” |
| 12 | `scripts/monitor_window_activity.py`、`scripts/monitor_gateway.py` | 两个 monitor 的输入、输出、临时性和缺失链路。 | “哪个会写项目日志，哪个会删除临时 DB？” |
| 13 | `src/perceptors/somatic_hub.py`、`pacing/real_pacemaker.py` | 旧链的数据模型和轮询方式。 | “它有没有读新 queue？”答案：没有。 |
| 14 | `src/app/app_bridge.py`、`src/mcp/server.py`、`src/mcp/tools.py` | 为什么 UI/MCP 是历史路径，哪些状态是硬编码。 | “旧 MCP 是否就是 FastMCP context server？”答案：不是。 |
| 15 | `src/actuators/`、`src/cortex/master_cortex.py` | 旧动作门、默认审批问题与新安全链的缺口。 | “一次动作从新 gateway 到审计结果是否已接通？”答案：没有。 |

## 6. 接管后的“脑内运行图”验收

当你能不看文件回答以下问题，就已经重新掌握了当前仓库：

1. 为什么 `WindowEventTicket` 不是 `NeuralMessage`？
2. 为什么 `PluginManifest`、`PluginGrant`、`PluginSession` 是三个对象？
3. session 路径中，哪一步发生在 SQLite 写入之前，为什么？
4. 为什么 state 可以 collapse、event 不可以？
5. 为什么 `CurrentContextReader` 不能算“中枢已经上线”？
6. 为什么启动 cockpit 后不能声称新 gateway 正在保护数据？
7. 哪些功能只在 mock/demo，哪些真的会对 Windows 或网络做 I/O？
8. 如果今后要实现第一个正式 daemon，它必须把哪些当前存在但未连接的部件**明确**连起来，又必须避免把哪些旧路径偷偷接入？

最后一个问题的答案不应通过猜测完成：在任何实现前，先将 daemon 的输入（manifest runtime 还是 built-in）、session 生命周期、queue consumer/ack、context 投影、MCP 生命周期、确认门、审计持久化与关闭/恢复语义逐条写成可验证契约。当前代码提供了部分砖块，尚未提供整栋楼。
