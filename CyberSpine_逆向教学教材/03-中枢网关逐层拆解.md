# 03：中枢网关逐层拆解（重点）

这一章只讨论 `src/core/` 和它与 `src/context/`、`src/sensing/` 的接缝。请把网关理解为“让一个消息**有资格**改变持久队列”的门，而不要理解成插件管理器、消息路由器、AI 大脑、worker 或执行器。

## 1. 一张完整调用图

```text
manifest JSON ──> load_manifest() ──> PluginManifest + SHA-256 digest
                                      │
local grant ──> PluginGrant ──────────┼──> RegistrationRegistry.register()
                                      │
runtime hello 参数 ───────────────────┴──> open_session() -> PluginSession

untrusted NeuralMessage + session
  -> NeuralSignalGateway.publish()
       1. registry.validate_session()
       2. AdmissionPolicy.admit()
            protocol/source/target/extensions/topic/kind/privacy/schema/time/TTL
            -> MessageLimits.validate_size()
            -> validate_payload()
       3. PluginHealthMonitor.assess()
       4. RateLimitPolicy.allow()
       5. audit.record(authorised)              [失败即停止]
       6. DurableEventQueue.enqueue()
       7. PluginHealthMonitor.observe(accepted)
       -> QueueItem(PENDING 或已合并的状态)

旧内置窗口消息（没有 session）
  -> NeuralSignalGateway.publish(message, None)
       -> _admit_legacy()
       -> audit.record()
       -> DurableEventQueue.enqueue()
```

右侧尚不存在：queue consumer、订阅路由、插件 subprocess、跨进程 token transport、持久审计、健康隔离执行器、从 queue 到 context 的通用 projector。

## 2. 第一层：统一信封 `NeuralMessage`

文件：`src/core/neural_message.py`。

`NeuralMessage` 是 Pydantic `BaseModel`。它不是 payload schema 本身，而是每个消息都有的“信封”：

| 字段 | 为什么需要 | 当前语义 |
|---|---|---|
| `protocol_version` | 协议升级时拒绝不兼容消息 | 默认 `1.0`；新 manifest 只接受 `1.0`。 |
| `message_id` | 队列主键、事件去重/投影定位 | 默认 `msg_` + UUID。 |
| `timestamp` | TTL 和未来时间偏斜检查 | 默认 UTC aware datetime。 |
| `kind` | 决定消息是状态、事件、指令、提议、结果、健康 | 网关外围插件 grant 只允许 state/event/health。 |
| `source` / `target` | 发送者和有向传递 | 上行外围消息必须 `source == session.plugin_id` 且 `target is None`。 |
| `topic` | capability / schema 的稳定业务名称 | 当前精确匹配，不支持通配符。 |
| `priority` | 为将来调度预留 | queue 当前不按 priority 排序。 |
| `privacy` | 可暴露范围的上限 | admission 对比 grant，context 只接收 public/metadata。 |
| `ttl_seconds` | 防止陈旧消息仍被消费 | queue 的读写状态转换都先 expire active message。 |
| `correlation_id` | 为将来关联链路预留 | audit 刻意不记录它。 |
| `payload_schema` | 让 payload 校验可定位 | 当前要求 `topic + @version`，并列在 manifest。 |
| `payload` | 业务事实本身 | 先经大小、类型、schema、敏感字段校验。 |
| `extensions` | 可扩展信封预留 | 目前非空直接拒绝，防止“扩展”绕过 schema。 |
| `collapse_key` | 最新 state 合并的键 | queue 只对 `STATE` 使用。 |
| `requires_ack` | 消费方确认需求 | queue 有 acknowledge API，但没有 consumer 自动读这个字段。 |

### `MessageKind` 不是所有类型都已接通

枚举列出 `STATE`、`EVENT`、`DIRECTIVE`、`PROPOSAL`、`RESULT`、`HEALTH`。这是协议野心，不是全部的已实现流：新插件 grant 和 legacy registration 都只接受前三类上行中实际安全的 `STATE/EVENT/HEALTH`；context 同样只 ingest 这三类；没有新路径实现 proposal → 用户确认 → result 的闭环。

## 3. 清单不等于权限，更不等于启动

文件：`plugin_manifest.py`。

### 3.1 `PluginRuntimeSpec`

它能描述两种 runtime：

- `kind="python"`：要求 `module:object` 格式 entrypoint；不能同时给 command/transport。
- `kind="process"`：要求 package-relative command，拒绝绝对路径、驱动器、`..`、NUL、URI 和 shell 元字符；transport 必须是 `cyberspine-jsonl@1`。

这些检查在 `load_manifest()` 时发生，目的只是把“以后可能执行的字符串”限制成安全声明。当前仓库没有任何代码根据它 import Python object、`subprocess.Popen()`、发现插件目录或建立 JSONL 通道。因此 manifest runtime 是**声明层 [实]，加载/生命周期层 [预留]**。

### 3.2 `PluginManifest`

`extra="forbid", frozen=True` 让未知字段立即失败并使模型不可变。它验证：

- `plugin_id` 是小写稳定 dotted identifier；
- version 符合 semver 样式；
- `protocol_version == "1.0"`；
- capabilities、schemas、permissions 无空字符串；
- `signal_schemas` 的 `@` 前 topic 集合必须与 capability 集合一一对应。

`load_manifest(data)` 不允许外部传 `manifest_digest`，而是将标准化 JSON (`sort_keys`、紧凑分隔符、ASCII) 做 SHA-256。这样 session 开启时可要求“运行时说的 digest 与注册时宣言完全相同”。它不签名、不验证发布者身份、也不提供磁盘 manifest 目录扫描。

### 3.3 `PluginGrant`：本机真正许可

文件：`plugin_registration.py`。

manifest 是插件说“我能发什么”，`PluginGrant` 是宿主说“我实际准许什么”。`RegistrationRegistry.register(manifest, grant)` 逐项检查：plugin id 相同、grant topic 非空且是 manifest capability 子集、kind 是 `{state,event,health}` 子集、grant 最大隐私不超过 manifest 声明。

如果删除 grant 而仅信任 manifest，任何插件可以自我声明敏感 capability 后立即取得权限。若把 grant 等同 manifest（演示脚本现在就是这样做），权限控制仍只是演示级的本地默认值。

## 4. session：把“声明已注册”缩小为“这个实例短期可信”

`RegistrationRegistry` 是内存字典：

```text
_registrations[plugin_id] = (PluginManifest, PluginGrant)
_sessions[session_id] = PluginSession
```

`open_session(plugin_id, instance_id, manifest_digest)`：

1. 拒绝空 instance id；
2. 要求 manifest 已注册且 digest 一致；
3. 拒绝同一 plugin + instance 已有未过期 session；
4. 用 `secrets.token_urlsafe()` 生成 session id 与 token，默认 TTL 300 秒。

`validate_session(session)` 会取存储的 session，常量时间比较 token，并要求整个 frozen dataclass 相等且未过期；过期时删除 session。它很适合单进程、测试或未来 adapter 的基础逻辑，但目前没有：

- token 随 IPC 的认证协议；
- session 的续期、撤销审计或持久化；
- 进程重启后恢复；
- manifest 版本升级时协调运行中的 process。

## 5. `AdmissionPolicy.admit()`：队列之前的逐项防线

文件：`gateway_admission.py`。这是最好读、也最应保持纯函数式边界的部分。其顺序重要：拒绝发生在持久化之前。

| 顺序 | 条件 | 失败代码 | 避免的风险 |
|---:|---|---|---|
| 1 | `validate_session(session)` | `session_invalid` | 伪造或过期实例。 |
| 2 | `message.protocol_version == manifest.protocol_version` | `protocol_unsupported` | 不同协议解释同一 payload。 |
| 3 | `source == session.plugin_id` | `source_mismatch` | 插件冒充另一个插件。 |
| 4 | `target is None` | `source_mismatch` | 上游末梢私自指定下游/绕路。 |
| 5 | `extensions` 为空 | `schema_invalid` | 未审核扩展字段藏数据。 |
| 6 | topic 在 grant | `topic_not_granted` | capability 越权。 |
| 7 | kind 在 grant | `kind_not_granted` | 外围插件发送 directive/proposal。 |
| 8 | privacy ≤ grant maximum | `privacy_exceeded` | 数据分类越界。 |
| 9 | schema 在 manifest 且 schema base == topic | `schema_invalid` | 用别的 schema 偷换 payload。 |
| 10 | timestamp aware、未来不超过 5 分钟、未 TTL 过期 | `timestamp_invalid` / `message_expired` | 伪造未来、陈旧重放。 |
| 11 | `MessageLimits.validate_size()` | `message_too_large` / `schema_invalid` | 内存、磁盘、深度/类型攻击。 |
| 12 | `validate_payload(schema, payload)` | `schema_invalid` / `privacy_exceeded` | 字段不匹配和敏感字段泄漏。 |

只有全部通过才原样返回同一消息。它不修改/“修复”客户端输入；这是正确的 fail-closed 风格：不明确的输入不进入队列。

## 6. payload 校验：为什么它目前是“窗口特化网关”

`schema_validation.py` 有一个 `WINDOW_PAYLOAD_VALIDATORS` 字典，仅含七个窗口 schema。每个验证器借助 `_map()` 做：

- type 必须是 mapping/list/scalar 的精确预期类型（注意 `bool` 不应被当成 int）；
- keys 必须完全在白名单，required keys 必须齐；
- key 经过大小写/符号归一化后不得包含 title、path、text、clipboard、keystroke、mousecoordinates、screenpixels、typedtext、password、content 等敏感词；唯一的刻意例外是布尔 `has_title`；
- 嵌套的 window/bounds/display/interaction/segment/summary 都递归验证。

这就是为什么一个 manifest 声明新的 `example.changed@1` 仍无法通过 `AdmissionPolicy`：它没有注册 payload validator。优点是不会“先收下再说”；缺点是目前所有新插件都要改核心 validator 才能进来，开放插件能力尚未实现。

## 7. 大小限制：防止合法 schema 被大 payload 滥用

`MessageLimits` 的默认值：总序列化 UTF-8 65,536 bytes、最大深度 8、单 dict/list 128 项、单字符串 8,192 bytes。`_validate_value()` 只允许 None、bool、int、float、str、dict、list/tuple；dict key 必须是 str。然后它把完整 `NeuralMessage.model_dump(mode="json")` 做 JSON 序列化后测总大小。

删掉它，schema 内合法的 `windows` 或 `changes` 数组、长应用名等可把 SQLite、日志和 consumer 内存撑大。仅有大小限制而没有 schema，则仍可能混入“合法大小的敏感字段”；二者不能互相替代。

## 8. `NeuralSignalGateway.publish()`：编排，不应承载业务推断

文件：`neural_gateway.py`。

### 8.1 新 manifest/session 路径

当 `session is not None`，`publish()` 创建 `HealthKey(plugin_id, instance_id)`，再尝试：

```text
registry.validate_session
admission.admit
health.assess
  PAUSED / QUARANTINED => instance_unhealthy
flow_control.allow
_record("admission", "authorized")
queue.enqueue
  queue 异常 => _record("delivery", "rejected", queue_unavailable)
health.observe(accepted=True)
```

`GatewayRejected` 分支会 `health.observe(accepted=False)`，并生成拒绝审计。审计的 source/topic 只有在 session 已可信、source 匹配、topic 已被 grant 的情况下才记；这避免攻击者把伪造的敏感文本塞进 audit metadata。

### 8.2 审计与 fail-closed

`_record()` 创建只含 action/outcome/plugin/instance/source/topic/reason/policy id/time 的 `AuditEvent`，没有 payload、correlation ID、token、PID、标题等字段。若 audit sink 抛异常，`_record()` 转换成 `audit_unavailable`。对授权路径而言，审计发生在 `queue.enqueue()` 前，因此 audit 不可用时消息不会改变 queue。

当前默认 `MemoryAuditSink` 只留在内存；它证明 API 顺序正确，不满足持久、可查询、跨进程审计要求。`monitor_gateway.py` 正是读取这个内存列表来显示聚合计数。

### 8.3 限流、健康、隔离

`RateLimitPolicy.allow(session, message)` 的 key 包含 plugin、instance、session id、topic。每个 key 有独立 token bucket，默认 capacity 30、每秒补 5。它在 admission 后、queue 前，因此被限流的数据不落库。

`PluginHealthMonitor` 维护：最后一次 observe 时间、拒绝数和 sticky state。默认阈值 3 degraded、5 paused、8 quarantined，60 秒未出现也是 degraded。一次成功不会自动抹除拒绝计数；`reset()` 是显式恢复 hook。`IsolationPolicy.decide()` 只返回 `suppress_upstream` 布尔决定，当前没有 runtime 管理器去真正停掉、隔离或重启插件。网关本身在下一次 publish 前检查 PAUSED/QUARANTINED，所以它能阻止后续入队，却不能阻止外部进程继续耗 CPU 或继续试发。

### 8.4 legacy 内置窗口路径

没有 session 时，gateway 先拒绝任何已经 manifest 注册的 source（防止绕过 session），再调用 `_admit_legacy()`。它只接受固定 source `peripheral.window.activity`、固定七 topic、`STATE/EVENT/HEALTH`、最大 `metadata_only`。它检查 protocol、topic、kind、privacy、target、timestamp、TTL，但**没有调用** `MessageLimits` 或 `validate_payload`。

这是一条非常重要的迁移债：`NeuralSpinalHub` 当前恰好走它，因此新 window 末梢在 hub 装配中没有进入 G1 schema/size 校验；gateway monitor 的 manifest/session 演示才会。不能因为同一个 `NeuralSignalGateway` 类名就假设安全级别相同。

## 9. 持久队列：已经实现的状态机，尚未实现的派发系统

文件：`event_queue.py`。

SQLite 表 `neural_messages`：

```text
message_id PRIMARY KEY
message_json      # 完整 NeuralMessage JSON
status
collapse_key
created_at / updated_at
delivery_attempts
```

### `enqueue()`

在 `RLock` 内先 `expire_messages()`。若消息是 `STATE` 且有 `collapse_key`，它找同 key 且 status 为 PENDING/DELIVERED 的记录，只选择其中早先的 **STATE**，用新 payload 覆盖旧 message JSON，但保留旧 `message_id`、created time、status 和 delivery attempts。EVENT 即便有同 key 也不合并，因为 transition 是历史事实。

否则插入 `PENDING`。这给“当前状态只需最新值、历史事件不能丢”一个明确实现。

### 读取和状态转换

- `get()`、`pending()`：读取前先过期。
- `mark_delivered()`：变为 DELIVERED，attempts +1。
- `acknowledge(id, status)`：只允许 ACKNOWLEDGED、DEFERRED、REJECTED、RESOLVED。
- `expire_messages()`：active 且 `message.is_expired(now)` 的记录变 EXPIRED。
- `status_counts()`：安全地只返回每种状态的数量，不回传 payload。

缺的不是一两个方法，而是整条 consumer 协议：谁读取 pending？如何加租约/锁？worker 崩溃后 DELIVERED 怎么重试？ACK 来自谁、如何认证？如何按 priority 排序？如何清理终态记录？这些都还不存在。因此 queue 是**可用存储部件**，不是完整“消息总线”。

## 10. Gateway 之后的 context：小而刻意的只读投影

`CurrentContextStore.ingest()` 不读取 queue；它接收调用者主动给它的已接纳 `NeuralMessage`。`NeuralSpinalHub.collect_window()` 显式保持顺序“publish 成功 → ingest”，所以被拒绝的消息不进入 context。

投影规则：

```text
STATE  -> states[topic] = payload      （最新覆盖）
HEALTH -> health[topic] = payload      （最新覆盖）
EVENT  -> recent_events（最多 32，按 message_id 可替换）
```

它再次拒绝 sensitive/restricted，即便上游错误放行。`snapshot()` 与 reader 都 deep copy，调用方不能通过返回 dict 回写内部状态。这个二次边界是有价值的，但它不能取代 gateway；绕过 gateway 直接调用 `ingest()` 的 Python 代码仍可能送入 public/metadata 的未验证 payload。

## 11. 网关“删掉一个部件会怎样”速查

| 删除/绕过 | 后果 |
|---|---|
| `PluginManifest` | 无稳定 plugin 身份、capability/schema/runtime 声明边界。 |
| `PluginGrant` | 插件自我声明即可取得权限，最小权限消失。 |
| session | 已注册 plugin 可被任意伪造 source 冒用，实例无法区分。 |
| `AdmissionPolicy` | queue 会接收错误来源、错误 topic、过期、敏感或结构不对的消息。 |
| `MessageLimits` | schema 合法但巨大/深嵌套 payload 可耗尽资源。 |
| `validate_payload` | 类型/字段/隐私关键词不能严格验证，窗口隐私契约不可执行。 |
| `RateLimitPolicy` | 一个 instance/topic 能高频填满 queue。 |
| `PluginHealthMonitor` | 重复拒绝/陈旧实例不形成状态，无法给控制面隔离依据。 |
| 审计前置 fail-closed | 入队发生却没有可信准入记录，安全事件无法追责。 |
| `DurableEventQueue` | 进程崩溃或暂时没有消费者时消息消失，无法记录 delivery 生命周期。 |
| state collapse | 高频 current-state 可能无限堆积；但绝不可拿它合并 EVENT。 |
| ContextStore 的二次隐私检查 | 一个错误注入点可把 sensitive payload 暴露给上层 reader。 |
