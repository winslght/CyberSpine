# 02：从入口到输出的真实执行路径

本章不按架构图想象系统，而是从“执行哪一个文件”开始走。仓库当前有多个入口，它们不是同一个程序的不同按钮。

## 1. 入口总表

| 入口 | 入口实际创建什么 | 最终输出 | 未创建什么 |
|---|---|---|---|
| `start_window_monitor.bat` | `monitor_window_activity.py`、`WindowActivityPeripheral`、WinEvent 源、可选 input hook、JSONL log | 终端仪表 + `runtime/logs` JSONL | 不创建 gateway、queue、context、MCP、执行器。 |
| `python scripts/monitor_gateway.py MANIFEST` | 临时 SQLite、Gateway、manifest registration、session、`GatewayMonitor` | 脱敏终端计数；临时目录退出即清理 | 没有 consumer、`CurrentContextStore`、MCP。 |
| `python scripts/monitor_gateway.py MANIFEST --window-snapshot` | 上述临时 gateway + `WindowActivityPeripheral` | 将真实窗口消息只入临时 queue 后显示计数 | 不调用 `NeuralSpinalHub`，不持久化到项目 runtime。 |
| `scripts/start_cockpit.bat` | pywebview 驾驶舱 + `CyberSpineAppBridge` + old hub/pacemaker | GUI | 不创建新 gateway、manifest session、新 context。 |
| `python src/mcp/server.py` | `CyberSpineMCPServer` + old `CyberSpineMCPHandlers` | JSON-RPC stdout | 不创建 FastMCP context adapter 或新 hub。 |
| `scripts/run_demo.bat` | `demo_minimal_loop.py` | 历史演示输出 | 不是新生产主线。 |

## 2. 最成熟的新运行路径：窗口观察器

### 2.1 启动

`start_window_monitor.bat` 定位项目根、选择 `.venv\Scripts\python.exe`（缺失时退回系统 Python），执行：

```text
scripts/monitor_window_activity.py --input-monitor
```

脚本 `main()` 解析时钟、刷新间隔、日志位置、输入监控开关和显示参数，构造：

```text
WindowActivityPeripheral(
  activity_window_seconds=...,
  focus_window_seconds=...,
  event_diagnostics_enabled=...
)
WindowActivityLog(path=...)
```

随后调用 `peripheral.start(input_monitor=args.input_monitor)`：

- `WindowsWindowEventSource.start()` 在独立 daemon thread 安装 9 类 `SetWinEventHook`。
- 如果用户通过命令显式要求 input monitor，`WindowsGlobalInputMonitor.start()` 才安装低级键盘/鼠标 hook。
- input hook 回调**不读取键值、文本、鼠标坐标或剪贴板**；只拿到当前 HWND 和时间，转交 `WindowInteractionTracker`。

非 Windows 平台下 event source 返回 false，目录读取返回空列表；这是安全降级而非跨平台完整实现。

### 2.2 事件到事实：为什么 callback 不直接发消息

```text
Windows WinEvent callback thread
  -> WindowEventTicket(kind, hwnd, monotonic time)
  -> queue.Queue
  -> WindowImpulseCoalescer.record()
  -> 200 ms 静默窗口完成
  -> WindowActivityPeripheral.collect_messages(tickets)
  -> WindowsWindowInventory / event affected window reads
  -> list[NeuralMessage]
```

回调中的工作刻意很少：筛选顶级窗口对象，创建票据，放队列。它不枚举窗口、不调 `psutil.Process()`、不验证 schema、不写 SQLite。原因是 WinEvent callback 是系统分发路径，慢操作会造成卡顿、重入或丢事件。真正的“事实读取”在观察脚本的调用线程进行。

### 2.3 `WindowActivityPeripheral.collect_messages()` 的内部步骤

文件：`src/sensing/window_activity.py`。

1. 清空上一轮未发布的 `_pending_geometry_changes`。
2. `_observed_catalog(event_tickets)` 选择读取策略：完整目录校准会从 `WindowsWindowInventory.list_windows()` 读取；事件批次可按受影响窗口和缓存重建目录。
3. 使用单调钟判断前台：`_resolve_foreground()` 的状态不是简单有/无，而是 `available`、`temporarily_unresolved`、`unresolved`（协议还预留 `unavailable`）。一次空前台读取会先保留已确认前台的短暂宽限，避免把短暂 shell 过渡误判为注意力中断。
4. `_decorate_catalog()` 给已采集的窗口附加派生事实：前台、驻留、交互频率、展示状态、几何活动等。
5. `_fact_signature()` 删除会随本地时钟变化的字段，并忽略系统表面，判断此批 WinEvent 是否真正改变用户窗口事实；相同签名的事件风暴不产生消息。
6. 无论是校准还是有变化的事件，生成三项基准事实：
   - `window.current_state@3`：当前前台和诊断计数；
   - `window.catalog@1`：可见窗口目录；
   - `window.time_window_summary@1`：驻留片段和统计。
7. 条件成立时再追加四类 transition：`focus_changed@2`、`high_interaction_changed@1`、`foreground_availability_changed@1`、`geometry_changed@1`。
8. 返回 `list[NeuralMessage]`，此时还没有 gateway、日志或上层 context。

### 2.4 消息事实和隐私边界

`_normalize_window()` / `_public_window()` 输出的核心是 `window_id`（由 HWND 派生）、应用进程名、PID、边框、Z 顺序、最小化/最大化/顶层、显示器几何和布尔 `has_title`。它没有输出窗口标题本身。

`WindowActivityPeripheral` 的所有消息都使用：

```text
source = peripheral.window.activity
privacy = metadata_only
kind = state 或 event
schema = 7 个 window.*@版本之一
```

这是代码中真实的“最小化采集”措施。它不代表整个旧 PoC（例如旧焦点 perceptor、旧 cockpit 文案）也同样不读取标题；应逐条检查旧路径。

### 2.5 观察器的四个节奏

`monitor_window_activity.py` 不只是 `while sleep(1)`：

| 节奏 | 调用 | 是否读取 Windows |
|---|---|---|
| 系统事件 | `wait_for_event_messages()` | 先阻塞等 ticket；ready 后读事实。 |
| 前台宽限到期 | `collect_foreground_resolution_messages()` | 只再读一次前台或缓存。 |
| 展示脉冲 | `collect_local_time_messages()` | **不读 OS**；只推进驻留/时间窗。 |
| 低频校准 | `collect_messages()` | 读完整窗口目录，补漏 event。 |

获得消息后脚本调用 `WindowActivityLog.append(messages)`（JSONL 写入）和 `_render_dashboard()`（终端）。到这里为止路径结束；数据没有进入新网关。

## 3. 新网关的可运行演示路径

### 3.1 普通状态观察

`scripts/monitor_gateway.py` 的 `main()`：

```text
manifest JSON
  -> load_manifest(json)
  -> TemporaryDirectory/signals.db
  -> DurableEventQueue
  -> NeuralSignalGateway(queue)
  -> gateway.register(manifest, PluginGrant.create(...))
  -> gateway.open_session(plugin_id, "gateway-monitor", manifest_digest)
  -> GatewayMonitor.render_snapshot()
```

这里 `PluginGrant.create(...manifest.capabilities)` 是演示脚本在本地直接授予 manifest 全部 capability 的做法。生产控制面尚不存在，不能把它误读为用户授权 UI 或安全策略数据库。

### 3.2 `--window-snapshot`：真实输入但临时输出

参数模式会额外构造 `WindowActivityPeripheral`，循环调用 `collect_messages()`。对每个返回消息：

```text
_publish_and_render()
  -> gateway.publish(message, session)
  -> 成功：临时 SQLite PENDING 记录
  -> 拒绝：吞掉 GatewayRejected（网关已留安全原因）
  -> GatewayMonitor.snapshot()
  -> 只显示队列各 status、授权/拒绝数、health、audit action/outcome、topic
```

关键的是：`TemporaryDirectory` 结束后 `signals.db` 被清理；代码显式释放 gateway 并 `gc.collect()`，以免 Windows SQLite 句柄阻止清理。因此它证明“消息可被 session 路径验证并入队”，**不**证明“数据已在系统中持久化并可被 AI 读取”。

### 3.3 `--governance-demo`：完全合成的 G2 演示

此模式构造 `window.geometry_changed` 的空 `changes` payload，使用人为 clock 和容量 1 的 token bucket，依次制造 accepted、rate_limited、recovered、paused、isolated。它适合看限流/健康/隔离状态如何改变；它不能证明真实插件被隔离、真实队列被消费者处理，或真实窗口产生这些事件。

## 4. 新路径装配器：它能怎样运行，实际又在哪里运行

`src/context/spinal_hub.py:NeuralSpinalHub` 是最短的新路径：

```text
__init__(database_path, window_peripheral=None)
  -> DurableEventQueue(database_path)
  -> NeuralSignalGateway(queue)
  -> CurrentContextStore()
  -> CurrentContextReader(self.current_context)
  -> WindowActivityPeripheral() 或注入的 fake
  -> gateway.register(PeripheralRegistration(... seven topics ...))

collect_window()
  -> window.collect_messages()
  -> gateway.publish(message)                 # legacy trusted path，无 session
  -> context.ingest(item.message)             # 仅成功入队后
  -> 返回 QueueItem 列表

read_current_context()
  -> reader.read_json()
```

这段是**真实可执行装配代码**，并被 `tests/context/test_spinal_hub.py` / `test_read_service.py` 用临时数据库和注入 snapshot 验证。但是检索当前脚本和 `src/` 的调用点，只找到测试对 `NeuralSpinalHub(...)` 的构造。没有一个 batch、Python `__main__` 或 app bridge 启动它。

注意另一个重要细节：这里使用 `PeripheralRegistration` 的 legacy trusted 入口；而 gateway monitor 使用 `PluginManifest + PluginGrant + PluginSession` 新入口。两者并存是迁移期兼容，不是已经统一的插件运行时。

## 5. 旧驾驶舱真实路径

```text
scripts/start_cockpit.bat
  -> src/app/cockpit_app.py:launch_cockpit_app()
  -> CyberSpineAppBridge()
       -> SomaticPerceptorHub()
       -> TemporalNeuralBuffer()
       -> MotorActuatorHub()
       -> LocalModelEngine()
       -> CognitiveTelemetryLogger()
       -> RealAutonomousPacemaker(interval=5, hub=old hub)
  -> pywebview window / src/ui/index.html
```

`CyberSpineAppBridge` 同时承担了构造服务、保存展示态、配置假数据、插件商店目录、调用模型、调用执行器和给前端序列化数据等角色。`_plugins_state`、`_cortex_config`、`_ganglion_models`、`_latest_briefing` 很多内容是硬编码字典。它们能让 UI 展示，不等价于真实 runtime 已安装模型、插件或建立到云端连接。

`RealAutonomousPacemaker` 是旧 pipeline 的后台节拍器：它轮询 `SomaticPerceptorHub`，生成历史的 tick 和 briefing；它不接收 `NeuralMessage`，不从 `DurableEventQueue` 消费，也不写 `CurrentContextStore`。

## 6. 旧 MCP 真实路径与安全含义

`src/mcp/server.py` 直接作为脚本运行时创建 `CyberSpineMCPServer`，后者通过 `CyberSpineMCPHandlers.get_instance()` 构造旧 app bridge。它手写 parse `initialize`、`tools/list`、`tools/call`，并把业务 `print` 改定向到 stderr，避免污染 JSON-RPC stdout。

它暴露世界简报、旧 somatic state、pacemaker ticks、telemetry、动作提议、quiet mode 等工具。`cyberspine_propose_motor_action` 会由 `tools.py` 构造 `ProposedAction`，再调用旧 `MotorActuatorHub.execute_action()`。

这条路径与新 `adapters/mcp/context_server.py` 完全不同：前者是手写、可启动、读写旧操作链；后者是 FastMCP、只读 context 工厂、未被启动。不要因为目录名都含 MCP 就以为它们共享同一安全门或消息模型。
