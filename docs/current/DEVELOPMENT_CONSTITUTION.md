# CyberSpine 开发宪法与授权 SOP

## 1. 目的与适用范围

本宪法保护用户对 CyberSpine 代码、配置、数据和运行环境的最终控制权。它适用于所有开发者、AI Agent、脚本、自动化流程和协作任务；与任何“默认主动实现”惯例冲突时，以本文件和仓库根目录 `AGENTS.md` 为准。

## 2. 授权模型

### 2.1 默认：仅讨论

除非用户在当前对话中明确给出含“**同意**”二字的实施授权，否则请求只能被理解为讨论、需求梳理、方案设计、审查、诊断或风险评估。

未授权状态允许只读操作，例如查看文件、检索代码、检查 Git 状态和运行不写入项目的诊断。未授权状态禁止创建、编辑、删除、生成或格式化项目文件，禁止安装依赖、修改配置、提交代码、创建分支、联网下载或执行其他外部副作用。

### 2.2 有效授权

有效授权必须同时满足：

1. 用户在当前轮明确使用“同意”；
2. 可识别的实施目标或范围；
3. 没有与既有约束冲突，或冲突已由用户明确裁决。

推荐表达：`我同意开发：<目标与范围>`。

“同意”不是无限期、全仓库或全权限授权。新任务、范围扩大或高风险操作均需要新的明确同意。

### 2.3 必须重新确认的事项

以下任一情况出现时必须暂停，并再次取得包含“同意”的授权：

- 修改扩展到未声明的模块、文件、功能或用户数据；
- 从局部修复变为重构、迁移、升级依赖或改变架构；
- 删除、覆盖、批量改写、迁移或处理难以恢复的数据；
- 访问网络、外部账户、云服务、设备或系统设置；
- 发送消息、发布、推送、创建 PR、提交或执行本机动作；
- 发现产品安全不变量可能被削弱或被绕过。

## 3. 标准开发流程

### 阶段 A：范围确认

获得授权后，先说明目标、拟改文件、非目标、风险和验证方式。范围无法从上下文安全推断时，先提问而不是假设。

### 阶段 B：最小实现

只改动实现已确认目标所需的内容。不得以“顺手优化”为由夹带无关改动、重命名、格式化、依赖升级或架构替换。

### 阶段 C：安全检查

保护现有未提交工作；不使用破坏性 Git 或文件操作；不删除失败测试、关闭防护逻辑或伪造验证结果。涉及敏感数据、插件、MCP、执行器、权限或跨进程通信时，按 `SECURITY_GUARDRAILS.md` 做专项检查。

### 阶段 D：验证

按风险选择测试、静态检查、协议验证或手工回归。验证应覆盖受影响的核心行为与相邻安全边界；无法执行的检查必须如实说明原因和风险。

### 阶段 E：交付与停止点

交付说明必须包含实际变动、验证证据、未验证项和残余风险。完成已授权范围后停止；下一步仅可作为建议，不能自动实施。

## 4. 工程行为准则

### 4.1 零附带伤害

新需求不能以破坏既有架构、测试、隐私防护、确认门控或用户工作区为代价。禁止通过删除测试、吞掉异常、修改无关全局状态或破坏周边功能来制造“完成”的假象。

### 4.2 根因与通用性

问题应在根因处修复。禁止只针对当前样例硬编码、用黑名单排除未知对象、将魔数散落在业务逻辑中，或依赖脆弱的内部实现细节。新增外部 API、依赖或配置前必须先核验其真实性、许可、维护状态和安全影响。

### 4.3 审计与可追溯性

安全相关决策、权限变化、确认状态和高风险操作应可从代码、配置、测试或日志中追溯。不可审计的便利实现不得替代明确的安全边界。

## 5. 复杂任务的审查

涉及高风险本机动作、敏感上下文、插件权限、MCP 协议、跨进程通信或重要架构演进的任务，应在实施完成后独立进行范围与安全审查。审查应区分：

- 已授权范围内的真实缺陷：可以提出修复建议；
- 新功能、偏好或扩大范围：记录为后续候选项，等待新的用户同意；
- 争议无法在合理轮次内收敛：停止扩展并由用户裁决。
