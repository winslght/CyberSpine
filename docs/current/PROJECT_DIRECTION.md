# 项目方向与主线开发章程

**状态：当前有效，约束后续设计与开发。**  
**适用范围：** CyberSpine 的产品主干、插件、协议、测试、文档与迁移决策。  
**优先级：** 本文件、[Demo 范围](DEMO_SCOPE.md)、[统一神经通信规范](UNIFIED_NEURAL_COMMUNICATION.md) 与用户明确指令优先于历史资料和旧代码。

## 1. 项目要建成什么

CyberSpine 是 Windows 本地环境的**可控感知与上下文基础设施**：它将用户明确授权范围内的桌面事实，转换为有隐私边界、可解释、可追溯的上下文，供本地推理服务和顶层大脑读取；任何改变系统的行为都必须经过独立确认门控。

项目的长期价值不在于“替用户自动点电脑”，而在于建立可扩展的本地事实层：新的末梢神经可以即插即用地提供新事实，旧模块不必因新增能力而重写。

### 核心产品目标：从事实到受控动作

CyberSpine 的每一条正式能力都应能落入以下链路：

```text
事实 → 假设 → 建议 → 用户确认 → 受控动作
```

- **事实**由末梢神经产生，必须可追溯到来源、时间、Schema 与权限范围；
- **假设**由神经中枢或本地推理服务产生，必须携带证据、置信度与不确定性；
- **建议**由顶层大脑面向用户提出，不能把假设叙述成确定事实；
- **用户确认**绑定具体动作、目标与风险，且不能被“系统已熟悉用户”替代；
- **受控动作**只由经过确认门控的执行器完成，并回写结构化结果以供后续观察。

这条链路是“更贴身的协助体验”和“用户仍保有控制权”能够同时成立的前提。

### 四层神经结构与职责边界

CyberSpine 按四层功能结构组织。它们可以在早期运行于同一进程，但职责、输入和输出必须保持可拆分：

```text
① 神经末梢 → ② 中枢网关 → ③ 神经中枢 → ④ 顶级大脑
```

| 层级 | 负责什么 | 典型输出 | 不得越界做什么 |
| --- | --- | --- | --- |
| ① 神经末梢 | 感知硬件和系统；在本地做与该感知源直接相关的初步事实整合 | 窗口焦点片段、专注占比、切换次数、交互强度 | 推断用户意图、给用户建议、直接执行动作 |
| ② 中枢网关 | 校验、授权、排队、去重、限流、持久化、审计和统一分发所有末梢信号 | 可可靠消费的标准化事实流与最新状态 | 重新采样末梢事实、计算某一末梢的业务统计、推断意图 |
| ③ 神经中枢 | 消费跨末梢事实，在本地形成可解释的上下文与假设 | 带证据、置信度与不确定性的假设 | 将假设伪装成事实、直接越过确认门控执行 |
| ④ 顶级大脑 | 结合长期目标、记忆和人格决定是否、何时、怎样与用户沟通 | 面向用户的建议、澄清与动作提议 | 伪造底层事实、替代用户确认、绕过受控执行器 |

末梢的“初步整合”只限于可由同一感知源验证的事实统计。例如窗口末梢可计算最近 30 分钟的焦点片段和专注比例；“用户可能正在写论文”必须由神经中枢基于多个事实形成，不能提前下沉到末梢。

## 2. 原型机与新主干

旧 Demo 是可行性原型，不是新架构的运行地基。它验证并保留以下产品闭环：

```text
感知有意义的变化 → 形成可解释上下文 → 提出有限建议
→ 用户确认 → 执行受控动作 → 记录结果
```

新主干以统一通信和可插拔模块重新实现这个闭环：

```text
末梢神经插件
→ NeuralMessage
→ 神经信号网关
→ 持久队列与神经中枢上下文
→ 本地推理服务 / 顶层大脑适配器
→ 确认门控
→ 执行器
→ result / 后续观察
```

旧代码只能承担两种角色：迁移期兼容适配器，或可重复的行为验收参考。新能力不得再直接加入旧的 `perceptors → pacing → app → mcp` 链路。

## 3. 不可变的架构原则

1. **一条内部消息主干。** 所有正式模块使用 `NeuralMessage` 和神经信号网关；不得为某个末梢神经再创造专用协议。
2. **一个事实源。** 每类操作系统事实只有一个正式采集者。例如窗口事实只由 `peripheral.window.activity` 采集；旧接口只能适配其输出，不能再独立采样。
3. **状态与事件分离。** `state` 表示最新可替换快照；`event` 表示变化历史。不得用轮询日志伪装为事件流。
4. **插件先声明、后运行。** 插件必须声明稳定 ID、入口、能力、Schema、权限、采样方式、隐私边界和健康检查。
5. **核心不绑定供应商。** `core` 不依赖 Windows、MCP、Ollama、GUI 或 UI；它们只能位于 `sensing`、`adapters`、`apps` 等边界层。
6. **最小权限与本地优先。** 采集端先脱敏；无法脱敏的数据不得进入上下文。动作必须经确认门控，默认不自动执行。
7. **可替换而非重复实现。** MCP 生命周期、Ollama 调用、OS 绑定、硬件监控、GUI 自动化和插件运行时优先采用成熟实现并包在适配器后；统一消息、隐私、调节、确认和上下文语义由 CyberSpine 自建。
8. **可观察与可回归。** 每条主干能力必须有 Schema、单元测试、至少一条集成测试和可供人查看的运行日志。

## 4. 长期模块边界

```text
src/core/       通信模型、队列、准入、安全与领域规则
src/sensing/    只读的 Windows/硬件事实采集、末梢内初步整合与末梢参考实现
src/context/    经网关投影的事实读取、跨末梢上下文与本地推理输入
src/actions/    受控执行器与动作结果
src/adapters/   MCP、模型、Windows、外部服务等可替换边界
src/apps/       CLI、桌面控制台和演示入口
plugins/        插件清单、权限声明与外部扩展
runtime/        本机队列、日志、缓存；不存放业务规则
```

依赖只允许从外向内：`apps → adapters → context/actions/sensing → core`。插件可依赖 `core` 和受控适配器，不能反向依赖 UI 或顶层大脑。

## 5. 当前第一个垂直切片：窗口感知

`peripheral.window.activity` 是新主干的第一个完整末梢神经。它只提供事实，不直接解释用户意图：

- 可见应用顶层窗口、应用名、PID、位置、尺寸、布局状态；
- 当前前台窗口和从观察开始/焦点切换起的驻留时间；
- 指定时间窗内按窗口归因的无内容交互频率；
- 前台切换与高频交互窗口集合变化。
- 窗口最大化/置顶状态、关联显示器、全屏几何候选，以及位置或尺寸变化；鼠标按住且边界变化时仅输出拖拽/调整大小候选。

它不记录或向统一消息输出键入内容、窗口标题、剪贴板、鼠标坐标或屏幕图像。神经中枢随后才可根据一段时间内的窗口集合、焦点序列、累计专注占比和交互强度形成工作模式假设；“查资料并写论文”属于假设，不是窗口插件直接输出的结论。

窗口感知的近期完善范围限于窗口层事实：全屏、置顶、窗口位置/尺寸变化和显示器归属。遮挡比例、透明度、像素级可见性、浏览器标签页、媒体播放状态和用户意图均不属于该末梢的当前范围。

窗口感知完成后，下一项必要能力是**窗口末梢的时间窗整合**：为每个窗口保留焦点片段、累计专注时长/占比、切换次数与交互统计，并将这些仍可验证的事实经网关交给后续层。仅有当前 exe 的驻留时长不足以判断用户意图。

## 6. 新 Demo 的阶段性交付

| 阶段 | 可验收产物 | 不做什么 |
| --- | --- | --- |
| A. 窗口事实层 | 窗口插件、清单、日志、目录/焦点/交互 Schema | 不推断意图，不执行动作。|
| B. 末梢时间窗整合 | 共享窗口事实源、焦点历史、累计专注占比、标准化只读事实接口 | 不启动模型，不主动打扰用户。|
| C. 工作模式提议 | 本地推理服务基于上下文给出带证据和置信度的只读假设 | 不将假设当成事实，不直接执行。|
| D. 顶层读取与确认 | MCP 读取上下文、提议动作、用户确认、单一低风险动作、结果回写 | 不允许无确认自动操作。|
| E. 扩展末梢神经 | 键鼠、系统、网络、存储等插件按同一规范接入 | 不为每个插件引入专有总线或中枢。|

每阶段完成前必须证明：核心测试通过、错误和隐私行为明确、日志可检查、旧兼容层没有成为新的事实源。

人格层、三层记忆和 Turbo 的设计边界见 [人格层、记忆与本机高上下文信任模式](MEMORY_AND_PERSONA.md)。它们不属于当前窗口感知闭环的默认能力，必须在独立阶段按安全前置条件实现。

## 7. 变更准入清单

每一个新模块、消息类别、插件能力或外部依赖，提交前必须回答：

1. 它属于哪个边界？输入、输出与唯一事实源是什么？
2. 使用哪一种 `NeuralMessage.kind`、topic 与 `payload_schema`？
3. 需要哪些权限？哪些数据明确不采集、不上传？
4. 失败、超时、重复、过期和停用时如何表现？
5. 是否存在成熟实现可采用？若自建，为什么属于 CyberSpine 核心语义？
6. 如何单独启停、观察、测试和回滚？
7. 它对最小闭环增加了什么可验收价值？

未能回答以上问题的探索只可进入 `experimental/`，不得接入主干。

## 8. 协议演进与兼容

- `1.x` 仅可新增可选字段、可协商能力或新的 Schema 版本；不得静默改变既有语义。
- 新旧接口共存时，必须明确“事实源”“兼容适配器”和退出条件；禁止双采样后长期并行。
- 旧 Demo 的接口要么有测试覆盖的适配器，要么进入 `legacy`，不得以“临时兼容”为名继续扩展。
- 对外适配器（MCP 等）只读取/写入核心定义的应用接口，不能绕过网关或上下文直接操作感知器。

## 9. 明确不做

- 不承诺全自动桌面 Agent，也不把主动唤醒模型当成默认能力；
- 不自建 GUI 自动化平台、硬件监控平台、通用消息中间件或大模型运行时；
- 不以“零 CPU”“完全事件驱动”等未经验证的营销语代替可测量指标；
- 不因追求宏大目录而一次性搬迁全部旧代码；迁移必须按能力和测试渐进完成。

## 10. 执行顺序

新开发按“先打通一条可观测、可确认、可回写的细链，再横向扩展”的方式进行。当前顺序为：

```text
窗口事实层
→ 末梢时间窗整合
→ 只读 MCP 读取
→ 工作模式提议
→ 确认门控与一个低风险动作
→ 动作结果回写
→ 新末梢神经横向接入
```

如果某项工作不强化这条主线，或绕开统一消息网关，它不应成为当前开发优先级。
